# Daymory 코드·UI·UX 검토

검토일: 2026-09-14. 기준: HEAD `103c545`와 기존 미커밋 `SketchbookScreens.kt` 변경.
소스 버전: 2.21.1 (153). 목적: 현재 구현을 정리하고 합리성과 감성 방향을 평가한다.

## 판단과 범위

**감성 방향은 일관적이다. 다만 반복 사용의 편의, 조작의 발견 가능성, 저장에 대한 신뢰는
그 시각적 방향만큼 정리되지 않았다.** 종이·책·문구라는 정체성을 유지하면서 조작과 상태 전달을
다듬는 것이 우선이다. 아래 평가는 사용성 실험 점수가 아닌 코드와 자료에 근거한 전문가 검토다.

- 실제 Kotlin 화면·공용 UI·저장/동기화 코드, 진행 기록, 최근 커밋을 확인했다.
- `image/UI design/`의 세로 PNG와 JPG 시안 2개, `design-tool/verify5.png`를 직접 열어 보았다.
  시안과 과거 캡처는 미감의 참고 자료이며 최신 앱의 렌더링 증거로 사용하지 않았다.
  `design-tool` 캡처의 파일 시각은 2026-08-21이다.
- 수정 중인 PPTX를 렌더링하거나 최신 실기기 화면을 촬영하지 않았다.
  ADB 연결 기기 목록이 비어 있어 실제 화면·터치·필압·프레임 성능은 확인하지 못했다.
- 앱 동작과 디자인은 변경하지 않았다. README를 실제 구조에 맞추고 이 검토와 진행 기록을 남긴다.

## 현재 구조와 좋은 결정

1. **Compose UI와 드로잉 엔진 분리**: `BrushView`가 픽셀·제스처·Undo를 담당하고
   `BrushControls`가 도구 UI를 담당한다. 기존 Android Canvas 엔진을 유지하는 구조가 목적에 맞다.
2. **기능별 저장소 분리**: `SketchbookRepository`, `DiaryRepository`, `ShareRepository`,
   `BackupRepository`의 역할이 나뉘어 있다. 로컬 우선 저장과 원격 병합이라는 방향도 분명하다.
3. **공통 디자인 기반**: `Theme.kt`, `Dimens.kt`, `SketchbookCover`, `MainTabPage`가
   화면마다 같은 요소를 다시 만드는 일을 줄인다. 실제 Composable을 쓰는 Preview도 유용하다.
4. **그리기 감각에 투자**: 종이 5종, 문구 형태 브러시, 수채화 합성, 스포이드와 팔레트는
   ‘손으로 기록하는 일상’이라는 제품 목적과 직접 연결된다.
5. **사용자 자율성**: 표지 사진/색, 색상 라이브러리, 도구바 도킹·최소화, 읽기 모드가
   자신의 노트를 만든다는 느낌을 준다. 전체 삭제 확인과 비파괴 내보내기도 적절하다.

아키텍처를 전면 교체할 이유는 보이지 않는다. 문제는 화면 파일에 누적된 상태와
저장 연결 코드의 중복, 그리고 공용 디자인 값에 예외 처리 기준이 부족하다는 점이다.

## 우선 해결할 발견 사항

### 1. P1 — Undo/Redo가 저장·공유 갱신을 알리지 않는다

근거: `brush/BrushView.kt:427`의 `undo()`와 `redo()`는 `restore()`와 `invalidate()`만
호출한다. 획 완료는 같은 파일의 `onStrokeEnd`를 통해 저장을 알린다.
세 편집 화면도 Undo/Redo 콜백에서 각각 `view?.undo()` / `view?.redo()`만 호출한다:
`sketchbook/SketchbookScreens.kt:1225`, `diary/DiaryScreens.kt:321`,
`share/SharedBookScreen.kt:433`.

따라서 마지막 동작이 Undo/Redo이면 그 변경으로 인한 자동저장·상대 화면 갱신이 발생하지 않는다.
후속 획이나 페이지 이동 등 다른 저장 계기가 있으면 반영될 수 있으므로, 모든 종료 경로에서
반드시 유실된다고 단정하지 않는다. 일기의 합성본과 필기 전용 파일도 따로 확인해야 한다.

권고: 성공한 내용 변경을 공통 이벤트로 전달하고 저장·공유가 이를 구독하게 한다.
일반 획, Undo/Redo, 채우기, 올가미 이동/삭제, 전체 지우기가 같은 계약을 갖도록 정리한다.
검증: 그림 → 저장 대기 → Undo만 실행 → 재열기 및 다른 기기 확인. Redo와 제스처 실행도 반복한다.

### 2. P1 — 실제 조작 영역과 접근성 동작이 부족하다

근거: `brush/BrushControls.kt:257`의 `ButtonTapSize = 30.dp`.
`BrushBtn`·`IconBtn`은 이 크기의 Box에 `bounceClick`을 붙인다.
`ui/Interactions.kt`의 `bounceClick`은 `pointerInput`/`detectTapGestures`만 사용하고
클릭 semantics, 키보드 활성화, 역할을 제공하지 않는다. 같은 구현이 로그인 CTA와 탭에도 쓰인다.

터치 사용자에게는 작은 도구 선택이 어렵고, TalkBack에는 표시 내용이 읽혀도 활성화 동작이
노출되지 않을 수 있다. Android 공식 문서는 최소 48dp 조작 영역과 표준 clickable의
접근성 동작을 설명한다. [Android Compose 접근성](https://developer.android.com/develop/ui/compose/accessibility/api-defaults)

권고: 아이콘의 시각 크기는 유지하고 입력 영역은 48dp 이상으로 확보한다. 눌림 애니메이션은
표준 `clickable`/`combinedClickable`과 함께 구현하고 선택·비활성 상태를 전달한다.
참고로 `Dimens.Screen.actionButtonSize = 32.dp`인 Material IconButton은 자동 터치 확장이
적용될 수 있으므로 코드상의 32dp만으로 실제 히트 영역을 단정하지 않는다. 런타임 경계를 확인한다.

### 3. P1 — 새 사용자를 위한 빈 화면 안내가 서로 반대다

근거: 홈 `ui/main/MainScreen.kt:217`은 “List 탭에서 첫 스케치북을 만들어보세요”,
목록 `sketchbook/SketchbookScreens.kt:537`은 “홈 화면에서 만들어보세요”라고 안내한다.
현재 만들기 액션은 목록 탭의 + 버튼에 있다. 공유 홈의 빈 화면도 List를 안내한다.

권고: 홈의 빈 화면에 생성 화면으로 이어지는 ‘첫 스케치북 만들기’를 제공하고,
목록에서는 바로 + 또는 같은 생성 액션을 안내한다. 공유의 빈 상태는 ‘초대 코드로 참여’와
‘공유 스케치북 만들기’를 해당 화면에서 찾을 수 있어야 한다.
검증: 책이 없는 계정으로 외부 설명 없이 첫 그림까지 도달하는지 확인한다.

### 4. P1 — 읽기 어려운 색 조합이 실제 기본값에 있다

| 대상 | 코드의 색 조합 | 계산 대비 |
|---|---|---:|
| 다크 메인 로고 | 검정 `#000000` / 배경 `#14171B` | 1.17:1 |
| 라이트 보조 글자 | `#858585` / surface `#FFFDF8` | 3.63:1 |
| 라이트 보조 글자 | `#858585` / background `#F4F0E7` | 3.24:1 |
| 기본 노란 목록 표지의 제목 | `#F3ECD9` / `#FFBF2A` | 1.40:1 |

근거: `ui/main/MainTabLayout.kt:186`의 고정 검정 로고,
`ui/theme/Theme.kt`의 `Grey`와 테마 색,
`sketchbook/SketchbookScreens.kt:681`의 고정 밝은 제목 및 `SketchbookCover.kt`의 기본 노랑.
수치는 불투명 sRGB 코드값을 WCAG 상대휘도 공식으로 계산한 것이며 렌더링 픽셀 측정값은 아니다.
사진 표지와 반투명 부제의 대비는 사진 내용에 따라 달라진다.

일반 크기 본문의 비교 기준은 4.5:1이다. 로고는 WCAG의 텍스트 대비 예외에 해당하므로
로고를 규정 위반으로 판정하지 않으며, 다크 모드에서의 시인성 문제로 다룬다.
[W3C 대비 기준](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)

권고: 로고는 테마별 명도 대응, 보조 글자는 더 진한 중성색, 표지 제목은
배경에 맞는 명도 또는 표지 바깥 제목 배치로 읽기 쉽게 한다. 과거에 제거한 스크림을
일괄 복원하기보다 확정된 표지 방향을 존중하며 해결한다.

### 5. P2 — 큰 고정 여백이 작은 화면의 본문 공간을 소모한다

근거: `ui/theme/Dimens.kt:17`부터 상단 60 + 브랜드 25 + 간격 40 + 제목 80 + 액션 60으로
본문 전까지 **265dp**, 하단에 추가 45dp를 예약한다. 좌우는 각 45dp다.
`MainTabLayout.kt`는 방향만으로 가로 레이아웃을 결정하며 본문/보조 패널 2:1을 유지한다.
`sidePanel`이 없을 때도 보조 열의 공간을 차지한다. 설정과 일기 탭은 이 기본값을 사용한다.

시안의 넉넉한 여백은 장점이지만, 높이가 낮은 가로 휴대폰이나 큰 글꼴에서는 내용이 밀리거나
과도하게 좁아질 위험이 있다. 현재 실기기에서 잘림을 재현했다는 의미는 아니다.

권고: 공통 헤더라는 결정은 유지하되 가용 폭·높이에 맞춘 치수 세트를 적용한다.
실제 내용이 없는 보조 열의 처리도 별도로 정한다. 360dp 폭, 짧은 가로 높이,
태블릿, 폴더블, 글자 1.0/1.3/2.0배에서 확인한다.

### 6. P2 — 익숙해지기 전까지 조작 규칙을 추측해야 한다

- 세로 목록은 한 번 탭해 열기, 가로 목록은 탭해 선택 후 더블탭 또는 패널 버튼으로 열기다.
  가로에는 명시적 열기 액션도 있으므로 더블탭만이 유일한 진입점은 아니다.
- 표지 편집은 길게 누르기, 도구바 이동도 길게 누르기,
  지우개 경계 블러는 선택된 지우개를 다시 누르기로 열린다.
- `MainActivity.kt:54`는 `remember { mutableStateOf(true) }`로 시작 화면을 매번 구성한다.
  로그인한 사람도 Activity 재생성/새 진입 시 다시 `enter`를 누르는 흐름이다.
- 제스처 설정의 Undo/Redo 명칭은 ‘뒤로가기/앞으로가기’여서 화면 이동과 혼동된다
  (`ui/main/MainScreen.kt:646`). 탭명도 Home/List/share/Diary/Other로 언어·대소문자가 섞여 있다.

권고: 처음 한 번의 짧은 안내나 액션 라벨을 보완한다. Undo/Redo는 ‘실행 취소/다시 실행’으로
통일하고, 장식적인 영문 제목과 실제 탐색 라벨의 역할을 구분한다.
가로 미리보기·아이콘 중심·롱프레스 도킹은 기록된 의도이므로 없애기보다 학습 단서를 보완한다.
시작 화면을 반복해서 보여줄지는 브랜드 의식과 재방문 편의를 비교해 별도 결정한다.

### 7. P1 — 동기화 신뢰 상태를 사용자가 알기 어렵다

근거: `RootViewModel.kt:104`는 백업 실패를 로그로만 남긴다.
`share/ShareRepository.kt:131`의 구독 취소도 마지막 상태를 유지할 뿐 UI 오류를 전달하지 않는다.
따라서 상대가 그리기를 멈춘 것과 동기화 실패를 사용자가 구분하기 어렵다.

색상 라이브러리는 별도의 확정된 잔여 위험도 있다. `data/ColorLibrarySync.kt`는
화면 scope에 500ms 지연 업로드를 예약하고, `backup/BackupSync.kt:63`의 병합은
같은 ID가 양쪽에 있으면 원격 값을 적용한다. 편집 화면을 빠르게 나가 업로드가 취소된 뒤
재동기화하면 마지막 로컬 색/이름 편집이 덮일 수 있다. PROGRESS.md에도 이미 보류된 이슈다.
단순 앱 백그라운드 전환만으로 항상 Compose scope가 취소되는 것은 아니다.

권고: ‘기기에 저장됨 / 동기화 중 / 다시 시도 필요’ 상태를 분리하고,
지연 저장 작업은 화면 수명과 분리하거나 미전송 변경을 보존한다.
실제 Firebase 연결·두 기기·오프라인 복귀 테스트로 확인한다.

## 감성적 설계 평가

| 관점 | 평가 | 근거와 보완 방향 |
|---|---|---|
| 정체성 | 명확함 | 오리, 틸·아이보리, 손글씨 제목, 책등과 종이 질감이 같은 세계를 표현한다. |
| 그리기의 감각 | 제품 목적에 적합 | 브러시 개선과 종이 합성이 실제 행위에 연결된다. 성능·필압의 체감 평가는 기기에서 필요하다. |
| 개인 소유감 | 잘 계획됨 | 표지 사진과 색, 나만의 색 라이브러리, 일기 달력이 기록을 개인화한다. |
| 편안함 | 보완 필요 | 저대비, 작은 터치 영역, 숨은 제스처는 차분한 외형과 별개로 사용에 긴장을 만든다. |
| 재방문 | 보완 여지 | 홈이 책 탐색 중심이다. 최근 기록을 이어가는 흐름과 반복 시작 화면의 비용을 함께 평가할 필요가 있다. |
| 함께하는 감정 | 기능은 있으나 설명 보완 필요 | 실제로는 각자의 캔버스를 함께 보는 방식이다. ‘한 장을 같이 편집’한다는 기대를 만들지 않도록 표현한다. |

과도한 장식 추가보다 **내 기록이 잘 보이고, 원한 동작이 쉽게 되고, 저장됐다는 안심을 주는 것**이
현재 브랜드 감성을 가장 크게 강화한다. 화면 감각은 이미 있으므로 사용자 작품이 주인공이 되도록
표지·도구·안내의 우선순위를 다듬는 방향이 적합하다.

## 코드 정리 순서

| 순서 | 정리 대상 | 이유 |
|---|---|---|
| 1 | 내용 변경 → 저장·공유의 공통 계약 | Undo/Redo 누락을 고치고 같은 종류의 누락 재발을 줄인다. |
| 2 | `Interactions.kt`의 공통 입력 처리 | 도구·로그인·탭의 접근성을 한곳에서 바로잡는다. |
| 3 | 세 편집 화면의 도구 상태·설정 연결 | 색/굵기/불투명도/도킹/제스처 배선 중복을 줄인다. 데이터 저장소는 용도별로 유지한다. |
| 4 | 큰 UI 파일의 책임별 분리 | 색상 편집, 라이브러리, 도킹, 달력 합성 등 독립된 책임을 작은 단위로 읽게 한다. |
| 5 | 타이포그래피·상태 색·적응형 치수 | `Dimens`는 이미 있지만 화면별 하드코딩과 예외가 많다. 서체도 Pretendard 선언과 실제 Typography 기본값이 일치하지 않는다. |

## 검증 기록과 다음 확인

- `git status --short`, 최근 10커밋, 변경 중인 SketchbookScreens diff를 확인했다.
- 접근성·대비 판단은 Android 및 W3C 공식 문서와 대조했다.
- `adb devices -l`: 연결된 기기 없음. APK 설치나 원격 데이터 변경은 수행하지 않았다.
- Android Studio JBR에서 `:app:testDebugUnitTest :app:lintDebug --offline --no-daemon` 실행을 시도했다.
  최초 제한 환경에서는 Gradle wrapper 접근이 실패했고, 일반 캐시를 이용한 재시도에서는
  `:app:processDebugResources`가 `R.jar` 삭제 IOException으로 실패했다.
  기존 진행 기록의 파일 잠금 증상과 일치하지만 이번에는 점유 프로세스를 특정하지 않았다.
  **테스트·앱 lint 완료 또는 통과로 보고하지 않는다.** 작업 중인 도구 프로세스는 종료하지 않았다.
- 현재 `local.properties`는 저장소 밖 PageCurl 모듈을 가리킨다. 재검증 시에는 사용 모듈을 명시하고,
  배포 재현성 검증은 저장소 안 `pagecurl/`을 사용하는 별도 깨끗한 환경에서도 해야 한다.
